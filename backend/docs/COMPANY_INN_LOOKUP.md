# Поиск реальной компании по ИНН (внешний справочник)

Функция: пользователь вводит ИНН → сервер делает **один** запрос к реальному
государственному реестру через посредника → сайт показывает найденную организацию
и честно названный источник → пользователь подтверждает → публичные реквизиты
сохраняются в **его собственный** профиль компании.

Это заменяет прежнее поведение, где `/companies/search` искал по локальной таблице,
а мастер сохранял вручную введённый ИНН. Локальный поиск **не** выдаётся за внешний реестр.

## Реальный источник

**DaData — findById/party** (`POST https://suggestions.dadata.ru/suggestions/api/4_1/rs/findById/party`).
Это публичные сведения **ЕГРЮЛ/ЕГРИП ФНС России**, отдаваемые через посредника DaData.

- Это **не** прямой запрос в ФНС и **не** подтверждение, что компания принадлежит пользователю.
- Аутентификация: заголовок `Authorization: Token <DADATA_API_KEY>` (серверный секрет).
- Официальная документация: <https://dadata.ru/api/find-party/>.
- DaData **не** гарантирует бесплатность: суточные лимиты зависят от тарифного плана.
  Платные аккаунты/тарифы в рамках задачи не оформлялись.

Выбор источника: в проекте не было готовой интеграции с реестром компаний; GigaChat/
Hackathon/OpenAI — это LLM, их для поиска реквизитов использовать нельзя. DaData —
официальный API с задокументированным форматом, без скрейпинга и обхода CAPTCHA.

## Что пользователь получает и чего источник не даёт

Получает (публичные реквизиты): наименование (краткое/полное), ИНН, КПП (у юрлиц),
ОГРН/ОГРНИП, дату ОГРН, регион (из юр. адреса), основной ОКВЭД (код + название + версия),
статус (действующая/ликвидируется/ликвидирована/банкрот/реорганизация), тип (юрлицо/ИП),
признак филиала.

Источник **не** подтверждает и функция **не** заявляет:
- что организация принадлежит пользователю (знание ИНН ≠ полномочия);
- платёжеспособность/финансы (наличие в реестре ≠ платёжеспособность);
- список выпускаемой продукции (ОКВЭД ≠ отрасль и ≠ номенклатура);
- место производства (юр. адрес ≠ производственная площадка).

Персональные данные (ФИО руководителей/учредителей, телефоны, email, доли, финансы)
**не** сохраняются — нормализатор их отбрасывает.

## Новые эндпоинты (аддитивно, обратная совместимость)

- `POST /api/v1/company-registry/lookup` — Bearer, тело `{ "inn": "<10 или 12 цифр>" }`.
  Принимает **только ИНН** (не URL). Делает один запрос к DaData. **Ничего не создаёт**
  (ни Company, ни membership, ни case-link, ни Impact/Scenario/Decision), профиль не меняет,
  LLM не вызывает. Возвращает кандидатов + короткоживущий `lookup_id`.
- `POST /api/v1/company-registry/confirm` — Bearer, тело `{ "lookup_id", "candidate_id" }`.
  Создаёт **собственный** рабочий профиль пользователя из публичных реквизитов (или открывает
  уже существующий его профиль с тем же ИНН). Серверное доверие к происхождению —
  по `lookup_id`, а не по присланному клиентом `provider`/`source`.

Совместимость: существующие API (регистрация, ручное создание компании `POST /companies`,
demo, case-context, agent loop, новости, финансы, Telegram) не менялись по контракту.
Формат ошибок — общий envelope `{ "error": { "code", "message", "details" } }`.

Отдельно починен ACL: `GET /companies/search` теперь ищет **только по компаниям пользователя**
(join membership по его `user.id`), а не по всей локальной таблице — чужие карточки больше
не раскрываются. Доступ по ИНН при этом **не** выдаётся.

Полный контракт полей — `contracts/openapi.json` (schemas `CompanyRegistryLookupOut`,
`RegistryCandidateOut`, `CompanyRegistryConfirmOut`) и `docs/MOBILE_API.md`.

## Валидация ИНН

Строка, ведущие нули сохраняются. Обрезаются только внешние пробелы. 10 цифр → юрлицо,
12 → ИП/физлицо. Проверяются контрольные разряды (10-значный: веса 2,4,10,3,5,9,4,6,8;
12-значный: два контрольных разряда). 12 цифр сами по себе **не** доказывают статус ИП —
это подтверждает только `type=INDIVIDUAL` из реестра. Причины отказа (`400 INVALID_INN`,
`details[0].reason`): `empty` | `non_digit` | `bad_length` | `bad_checksum`.

## Безопасность и эксплуатация

- **Ключ только на backend.** Никогда не в `VITE_*` / web/.env / браузере. Frontend вызывает
  только наши `/company-registry/*`; ключ не передаётся frontend, scheduler и Telegram worker.
- Запрос только на фиксированный разрешённый URL DaData. `follow_redirects=False` — заголовок
  `Authorization` не переотправляется на другой хост при redirect (redirect → `REGISTRY_BAD_RESPONSE`).
- Поиск **не** шлётся на каждый введённый символ — только по явной кнопке «Найти компанию».
- Кэш хранит **только** успешные публичные ответы (per-process, TTL
  `COMPANY_REGISTRY_CACHE_TTL_SECONDS`); не хранит пользовательские финансы, права доступа или
  внутренний CompanyContext. Ошибки авторизации/временные сбои **не** кешируются как `not_found`.
- Логи без ключей, без `Authorization` и без полных персональных ответов.
- Ошибки источника **не** разлогинивают пользователя: upstream 401/403 → наш `503 REGISTRY_AUTH_ERROR`
  (а не `401`). Ошибка источника **не** превращается в «компания не существует». Секрет и сырой
  ответ провайдера наружу не отдаются.

### Границы rate limit / cache при многопроцессном запуске

Per-user rate limit (`COMPANY_REGISTRY_USER_RATE_PER_MINUTE`) и кэш ответов —
**в памяти процесса**. При нескольких воркерах uvicorn лимит/кэш считаются **на процесс**
(эффективный лимит = N_процессов × значение; попадание в кэш зависит от процесса).
Серверное подтверждение (`lookup_id`) намеренно хранится в БД (таблица
`company_registry_lookups`), а не в памяти — поэтому confirm корректен при любом числе
процессов. Redis ради этой функции не вводился (не требуется для корректности).

## Подтверждение и provenance

- Дубликаты ищутся **только среди компаний пользователя** (по `tax_id` в его membership).
  Нашлась своя — возвращается `opened_existing=true`, новая не создаётся. Чужую Company
  знание ИНН **не** открывает и её наличие/данные не раскрываются.
- Настоящий ИНН **не** связывается с обезличенными `U_*` организаторов; `case_org_company_links`
  и membership в чужой Company автоматически не создаются.
- Реквизиты из реестра помечаются в `company_profile_settings.preferences_json`
  (`registry_provenance.fields_from_registry`). Отредактировал поле — оно переходит в
  `fields_overridden_manually` и больше не «проверено реестром». `verified_scope` =
  `public_requisites` (не вся компания, не полномочия).
- confirm **не** перезаписывает: поставщиков, рынки сбыта, валюты, финансовые параметры,
  цепочки поставок, доли выпуска, банковские продукты, конкурсный контекст.
- ОКВЭД → отрасль: только грубая детерминированная **подсказка** (`suggested_industry`),
  не применяется автоматически.

## Конфигурация

| Переменная (env, backend) | Default | Назначение |
|---|---|---|
| `DADATA_API_KEY` | пусто | Ключ DaData. Пусто → `status=not_configured`, ручной ввод работает |
| `COMPANY_REGISTRY_TIMEOUT_SECONDS` | `6.0` | Таймаут запроса к источнику |
| `COMPANY_REGISTRY_MAX_CANDIDATES` | `10` | Сколько кандидатов вернуть |
| `COMPANY_REGISTRY_MAX_RESPONSE_BYTES` | `1000000` | Ограничение размера ответа источника |
| `COMPANY_REGISTRY_CACHE_TTL_SECONDS` | `3600` | TTL кэша успешных ответов (per-process) |
| `COMPANY_REGISTRY_USER_RATE_PER_MINUTE` | `20` | Per-user лимит (per-process) |
| `COMPANY_REGISTRY_LOOKUP_TTL_SECONDS` | `900` | Время жизни `lookup_id` (в БД) |

Отсутствие ключа **не** заменяется демо-ответом: приложение запускается и работает с ручным
заполнением. Ключ секретный: в чат не присылается, в root `.env` не добавляется.

### Compose / stand.env

- `docker-compose.competition.yml`: `DADATA_API_KEY` проброшен **только** в сервис `api`
  (не в `web`, `news_scheduler`, `telegram_*`).
- `docker/competition/entrypoint-api.sh`: `DADATA_API_KEY` — runtime-only секрет (как
  `HACKATHON_API_KEY`), из `stand.env` не читается. Runtime-параметры `COMPANY_REGISTRY_*`
  из `stand.env` **не** теряются (не входят в skip-list — пробрасываются как есть).

`company_registry_lookups` (idempotent, с индексами по `user_id` и `inn`). Проверялась на

## Live-проверка: NOT_VERIFIED

`DADATA_API_KEY` не найден ни в shell-окружении, ни в `*.env`/`stand.env`. Поэтому реальный
(live) поиск по DaData помечается **NOT_VERIFIED**: с реальным ключом он не запускался.
Mocked/integration-проверки пройдены. Чтобы проверить вживую: задать `DADATA_API_KEY` в
серверном окружении (компоуз `api` или `.env`), затем `POST /api/v1/company-registry/lookup`
с реальным ИНН под Bearer-токеном. Один ограниченный read-only lookup допустим; ключ в ответах/
логах не печатать.

## Ручной чеклист браузерной проверки (DOM)

1. `/company/setup`, шаг «Данные компании»: ввести валидный ИНН, нажать «Найти компанию».
   Без ключа — сообщение «поиск не подключён», ручные поля работают.
2. Невалидный ИНН (контрольная цифра) → инлайн-ошибка, запрос не уходит.
3. С ключом и реальным ИНН: карточка с наименованием, ИНН/КПП/ОГРН, регионом, ОКВЭД,
   статусом и честной строкой источника (DaData · ЕГРЮЛ/ЕГРИП, «не прямой запрос в ФНС»).
4. Несколько кандидатов (головная + филиалы) → показаны все, авто-выбора нет.
5. Ликвидированная организация → статус показан явно.
6. «Использовать эти данные» → профиль создан/открыт; на шаге «Роль и отрасль» — подсказка
   отрасли по ОКВЭД (не подставлена автоматически).
7. `/company`: блок «Происхождение реквизитов» — какие поля из реестра, какие изменены вручную.
8. Отредактировать название в профиле → поле уходит в «изменено вручную».

## Оставшиеся ограничения

- Live-поиск не проверен (нет ключа) — см. NOT_VERIFIED.
- Нет полноценной браузерной DOM-проверки (инструмент для автоматизированного DOM в этой
  сессии не применялся по условию без скриншотов/CDP) — только helper-тесты и проверка исходника.
- Rate limit/cache — per-process (см. раздел выше). При горизонтальном масштабировании точный
  глобальный лимит потребует общего стораджа (намеренно не вводился).
- Доступны только публичные реквизиты DaData; суточные лимиты зависят от тарифа DaData.
