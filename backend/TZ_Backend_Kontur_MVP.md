# Техническое задание: backend MVP «Контур»

**Версия:** 1.0  
**Назначение:** документ для backend-, frontend- и product-команды Альфа-хакатона  
**Целевая платформа:** мобильное приложение + Telegram-бот  
**Статус:** MVP, одна демонстрационная компания, объяснимые правила, подготовленные данные

---

## 1. Коротко о продукте

«Контур» помогает руководителю понять не просто **что произошло**, а **что событие означает для конкретной компании и какие варианты действий есть**.

Основной пользовательский путь:

> **Событие → связь с компанией → последствия → варианты действий → сравнение сценариев → решение человека**

Продукт состоит из пяти смысловых модулей:

1. **Digital Twin** — структурированный профиль компании и её зависимостей.
2. **Event Intelligence** — события, источники и нормализованные данные о них.
3. **Impact Graph** — проверяемая цепочка, по которой событие может повлиять на компанию.
4. **Solution Engine** — возможные меры и альтернативы.
5. **Scenario Simulator** — сравнение последствий вариантов.

Мобильное приложение — основной интерфейс работы. Telegram — дополнительный канал срочных уведомлений с переходом в соответствующий экран приложения. Бот не заменяет приложение и не принимает бизнес-решение за пользователя.

## 2. Цели и границы первой версии

### Цель MVP

Полностью пройти демонстрационный сценарий для компании «СеверПром»:

> ограничение экспорта электроники из Китая → поставщик Shenzhen X → компонент B → линия №2 → под риском 24% выпуска → сравнение трёх альтернатив → симуляция → сохранение плана действий → уведомление в Telegram.

### В MVP входит

- регистрация, вход и подтверждение почты;
- создание и редактирование профиля компании;
- поставщики, продукты, площадки, производственные линии и выбранные финансовые факторы;
- демонстрационные события с источниками и метками «факт / предположение / оценка»;
- ранжирование событий для компании;
- объяснимая цепочка влияния;
- подготовленные варианты решений;
- детерминированный расчёт сценария;
- сохранение решения и следующих шагов;
- Telegram-уведомление владельцу в личный чат;
- подключение Telegram-группы как дополнительный канал;
- настройки порога и типов уведомлений;
- Swagger/OpenAPI, seed-данные и базовые тесты.

### Не входит в первую версию

- сбор новостей из множества реальных источников в реальном времени;
- автоматическое подтверждение фактов, прогнозов или доступности поставщиков;
- финансовые рекомендации и гарантированные оценки потерь;
- универсальный цифровой двойник любого бизнеса;
- полноценная система управления закупками;
- AI-агенты, самостоятельно меняющие профиль, выбирающие поставщика или рассылающие решения;
- сложный графовый движок, микросервисы, отдельное хранилище векторов.

Для демо используются заранее подготовленные данные. Все демонстрационные поставщики, проценты, сроки и расчёты явно помечаются как оценочные.

## 3. Соответствие макету мобильного приложения

Backend должен поддерживать уже подготовленный сценарий из 18 мобильных экранов — от приветствия и регистрации до сохранённого решения. В интерфейсе используются короткие русскоязычные поля, статусы и подписи; API возвращает структуру данных, а не готовые строки интерфейса там, где это возможно.

| Экран макета | Что должен поддержать backend |
|---|---|
| 01 Начало | Публичный экран, API не требуется |
| 02 Создать аккаунт | Создание пользователя |
| 03 Подтверждение почты | Выдача и проверка кода подтверждения |
| 04 Добавим компанию | Поиск демо-компании по названию/ИНН или ручное создание |
| 05 Проверьте данные | Получение и подтверждение карточки компании, роль пользователя |
| 06 Чем занимается бизнес | Список отраслей и сохранение отрасли |
| 07 Что производите | Создание и изменение продуктов |
| 08 Ключевые поставщики | Создание и изменение поставщиков и закупаемых компонентов |
| 09 Где работает бизнес | Площадки, линии, доля выпуска и регионы продаж |
| 10 Финансовые факторы | Валюты закупок и необязательные финансовые параметры |
| 11 Проверьте профиль | Сводный профиль, предупреждения о незаполненных связях |
| 12 Модель создана | Статус построения и покрытие связей Digital Twin |
| 13 Обзор | Счётчики событий и приоритетная лента |
| 14 Событие | Детали события, источники, факты, предположения и уверенность |
| 15 Цепочка влияния | Упорядоченный Impact Graph и возможный эффект |
| 16 Варианты действий | Список альтернатив с ценой, сроком, риском и совместимостью |
| 17 Сравнение сценариев | Результаты симуляции для базового и альтернативного сценариев |
| 18 План действий | Сохранённое решение, ожидаемый эффект и следующие шаги |

### Дополнение к макету: Telegram и уведомления

В текущих 18 экранах нет настройки Telegram. Добавить экран **«Уведомления → Telegram»** (экран 19 или раздел настроек компании):

- статус личного подключения: «Не подключён / Ожидаем подтверждения / Подключён»;
- действие «Подключить личный Telegram»;
- действие «Добавить бота в группу» и состояние подтверждения группы;
- выбор минимального уровня важности;
- переключатели «Риски», «Возможности», «Ежедневная сводка»;
- тихие часы или пауза уведомлений;
- кнопка отключения канала.

Подключение необязательно: пользователь может завершить онбординг и пользоваться приложением без Telegram.

## 4. Рекомендуемая архитектура

### Формат

**Модульный монолит** с одной базой PostgreSQL. Это проще поддерживать и быстрее демонстрировать, чем набор сервисов.

Предлагаемый стек, если команда ещё не выбрала свой:

- Python + FastAPI;
- PostgreSQL;
- SQLAlchemy + Alembic;
- Pydantic-схемы;
- фоновый worker для отправки уведомлений;
- Docker Compose для локального запуска;
- pytest для тестов.

Если команда уже уверенно работает с другим стеком, сохраняем архитектуру и API-контракт, а не переписываемся под инструменты.

### Модули backend

1. `auth` — пользователи, сессии, подтверждение почты.
2. `companies` — компания и профиль Digital Twin.
3. `graph` — узлы, связи и поиск путей влияния.
4. `events` — события, источники, категории, сопоставление с компаниями.
5. `solutions` — варианты действий и их параметры.
6. `scenarios` — расчёт и хранение результатов симуляции.
7. `decisions` — выбранные решения и action items.
8. `notifications` — правила подписки, очередь и журнал доставки.
9. `telegram` — связь аккаунта/группы, команды бота и отправка сообщений.

Все мобильные endpoint’ы имеют общий префикс `/api/v1`. Входящие команды Telegram обрабатываются отдельным webhook endpoint или процессом polling; они используют те же application services, что и REST API.

## 5. Модель данных

Названия таблиц можно адаптировать под стиль репозитория, но связи и смысл полей должны сохраниться.

### Пользователи и доступ

- **users**: `id`, `email`, `password_hash`, `display_name`, `email_verified_at`, `created_at`.
- **company_memberships**: `user_id`, `company_id`, `role`, `created_at`.
- Роли MVP: `owner`, `admin`, `analyst`, `viewer`. На демо достаточно владельца и участника.

### Профиль компании и Digital Twin

- **companies**: `id`, `name`, `legal_name`, `tax_id`, `industry`, `size_band`, `hq_region`, `created_by`, `created_at`, `updated_at`.
- **company_nodes**: `id`, `company_id`, `node_type`, `name`, `attributes_json`, `status`.
- Типы узлов MVP: `supplier`, `component`, `product`, `facility`, `production_line`, `market`, `currency`, `loan`.
- **company_edges**: `id`, `company_id`, `from_node_id`, `relation_type`, `to_node_id`, `attributes_json`, `confidence`, `source_type`.
- Типы связей: `buys_from`, `supplies`, `used_in`, `produced_at`, `sold_in`, `priced_in`, `financed_by`.
- **company_profile_settings**: предпочтения и необязательные параметры компании; чувствительные финансовые сведения не должны быть обязательны для онбординга.

В `attributes_json` не хранить единственную копию бизнес-критичных значений. Для критичных полей (например, доля выпуска линии) определить типизированные колонки либо валидируемую схему.

### События и объяснимость

- **events**: `id`, `title`, `summary`, `category`, `event_type`, `severity`, `occurred_at`, `effective_from`, `status`, `created_at`.
- **event_sources**: `id`, `event_id`, `publisher`, `url`, `published_at`, `source_quality`, `excerpt`.
- **event_impacts**: `id`, `event_id`, `company_id`, `impact_score`, `urgency`, `confidence`, `reason_summary`, `computed_at`.
- **impact_paths**: `id`, `event_impact_id`, `path_nodes_json`, `path_edges_json`, `exposure_value`, `claim_type`, `explanation`.
- `claim_type`: `confirmed_fact`, `inference`, `assumption`, `estimate`.

Событие может затрагивать категорию, страну, валюту или тип сырья без прямого упоминания компании. Эти условия хранятся в структурированных атрибутах события, а не только в тексте заголовка.

### Решения и сценарии

- **solution_candidates**: `id`, `event_impact_id`, `name`, `country`, `cost_delta_percent`, `lead_time_days`, `risk_percent`, `compatibility`, `availability_status`, `is_demo`.
- **scenarios**: `id`, `company_id`, `event_id`, `solution_id`, `created_by`, `parameters_json`, `results_json`, `model_version`, `created_at`.
- **decisions**: `id`, `scenario_id`, `status`, `decision_note`, `created_by`, `created_at`.
- **action_items**: `id`, `decision_id`, `title`, `status`, `assignee_user_id`, `due_at`, `created_at`.
- Статусы решения MVP: `draft`, `selected`, `cancelled`.

### Telegram и доставка

- **notification_subscriptions**: `id`, `company_id`, `user_id`, `channel_type`, `chat_id`, `chat_title`, `min_severity`, `event_categories_json`, `risks_enabled`, `opportunities_enabled`, `digest_enabled`, `quiet_hours_json`, `timezone`, `is_active`, `verified_at`.
- `channel_type`: `telegram_private` или `telegram_group`.
- **telegram_link_tokens**: `id`, `user_id`, `token_hash`, `expires_at`, `consumed_at`.
- **notification_outbox**: `id`, `company_id`, `event_impact_id`, `channel_type`, `chat_id`, `payload_json`, `dedupe_key`, `status`, `attempts`, `next_attempt_at`, `sent_at`, `last_error`.
- Уникальность `dedupe_key` предотвращает повторную отправку одного и того же события в один канал.
- **telegram_updates** (или эквивалент): `update_id`, `received_at`, `processed_at`, `result` — для идемпотентной обработки входящих обновлений.

## 6. API-контракт мобильного приложения

Формат JSON — `snake_case`, даты — ISO 8601 UTC. Ошибки возвращаются одинаково:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте введённые данные",
    "details": [{"field": "tax_id", "reason": "invalid_format"}]
  }
}
```

### Аутентификация

- `POST /auth/register` — email, пароль, имя.
- `POST /auth/verify-email` — email и код подтверждения.
- `POST /auth/login` — access/refresh token.
- `POST /auth/refresh` — обновить access token.
- `GET /users/me` — текущий пользователь и доступные компании.

Для демо можно добавить отдельный seed-user режим, но его нельзя включать незаметно в production-конфигурации.

### Онбординг и профиль

- `GET /companies/search?q=...` — поиск по названию/ИНН среди seed-данных/доступного справочника.
- `POST /companies` — создать компанию вручную.
- `GET /companies/{company_id}/profile` — профиль с узлами, связями и заполненностью.
- `PATCH /companies/{company_id}` — основная карточка и отрасль.
- `POST /companies/{company_id}/nodes` — добавить поставщика, продукт, площадку, линию, рынок и т.п.
- `PATCH /companies/{company_id}/nodes/{node_id}` — изменить узел.
- `POST /companies/{company_id}/edges` — добавить/изменить связь между узлами.
- `POST /companies/{company_id}/profile/complete` — проверить обязательные поля и отметить профиль готовым.
- `POST /companies/{company_id}/digital-twin/build` — построить/пересчитать демо-граф; возвращает `status` и число связей.

Профиль должен сохраняться по мере прохождения онбординга. Пользователь может закрыть приложение и продолжить позже. Финансовый шаг необязателен.

### Обзор и события

- `GET /companies/{company_id}/dashboard` — агрегаты и приоритетные карточки для экрана 13.
- `GET /companies/{company_id}/events?status=action_required&cursor=...` — лента.
- `GET /events/{event_id}?company_id=...` — детали события для экрана 14.
- `GET /events/{event_id}/impact?company_id=...` — пути графа для экрана 15.
- `POST /events/{event_id}/recompute-impact` — пересчёт для демо/администратора.

Пример краткого объекта события:

```json
{
  "id": "evt_china_export_001",
  "title": "Китай ограничивает экспорт электроники",
  "category": "geopolitics",
  "priority": "high",
  "impact_score": 92,
  "urgency": "watch_now",
  "confidence": 0.78,
  "reason_summary": "Ограничение связано с компонентом B у Shenzhen X.",
  "exposure": {"label": "Доля выпуска под риском", "value": 24, "unit": "percent"},
  "claims": {"confirmed": 2, "inferences": 1, "assumptions": 1},
  "source_count": 1,
  "updated_at": "2026-10-10T09:30:00Z"
}
```

### Варианты и симуляция

- `GET /events/{event_id}/solutions?company_id=...` — варианты для экрана 16.
- `POST /events/{event_id}/simulate` — вход: `solution_id`, `inventory_days`, `delay_days`, дополнительные параметры; выход: сравнение baseline и выбранного сценария.
- `GET /scenarios/{scenario_id}` — получить сохранённый расчёт.
- `POST /decisions` — сохранить сценарий как выбранное решение.
- `POST /decisions/{decision_id}/action-items` — добавить следующий шаг.
- `PATCH /action-items/{action_item_id}` — изменить статус/ответственного.

Результат симуляции должен включать `model_version`, использованные параметры и пометку `is_estimate`. Не возвращать только итоговые проценты без объяснения, откуда они взялись.

### Уведомления и Telegram

- `GET /companies/{company_id}/notification-settings` — состояние и настройки каналов.
- `POST /telegram/link-token` — выпустить одноразовый токен привязки; срок действия 10 минут.
- `POST /telegram/groups/link-token` — выпустить токен привязки группы для владельца/администратора.
- `PATCH /notification-subscriptions/{id}` — уровень важности, категории, тихие часы, типы событий.
- `DELETE /notification-subscriptions/{id}` — отключить канал.
- `POST /telegram/webhook` — принимать Telegram updates в webhook-режиме (если выбран он).

В личном Telegram сценарий такой: владелец нажимает «Подключить Telegram» в приложении → открывает ссылку на бота с одноразовым параметром → нажимает Start → backend проверяет, что токен существует, не истёк и ещё не использован → создаёт личную подписку.

Для группы владелец добавляет бота, затем подтверждает привязку группы одноразовым кодом. По возможности закрепить/проверить право администратора. Привязка должна требовать подтверждения пользователя, имеющего доступ к компании.

## 7. Impact Graph и ранжирование

### Представление связей

Граф хранится в `company_nodes` и `company_edges`; для MVP пути вычисляются обычными SQL-запросами или кодом приложения с ограниченной глубиной, например до 5 переходов. Циклы предотвращаются через список посещённых узлов. Не требуется отдельная графовая БД.

Пример пути:

```text
Ограничение экспорта
  → страна поставщика: Китай
  → Shenzhen X
  → компонент B
  → линия №2
  → 24% выпуска
```

### Сопоставление события

Каждое demo-событие имеет структурированные признаки: затронутые страны/категории/валюты/виды сырья, тяжесть, период действия и качество источника. Правила MVP сопоставляют признаки с узлами и связями Digital Twin. Не полагаться только на совпадение слов в заголовке.

### Оценки

- **Impact score (0–100)** — приоритет возможного влияния.
- **Urgency** — насколько скоро событие требует внимания.
- **Confidence (0–1)** — насколько надёжны источники и связи.

Impact и confidence нельзя объединять в один показатель. Высокое влияние при низкой уверенности должно отображаться именно так и сопровождаться объяснением.

Для MVP реализовать версионируемую детерминированную формулу. Например:

`impact_score = 0.40 × severity + 0.30 × exposure + 0.20 × dependency_criticality + 0.10 × propagation_proximity`

Все компоненты нормализованы в диапазон 0–100; веса вынести в конфигурацию. Значение 92 из макета — демонстрационное, оно не должно быть захардкожено для любого события.

Confidence рассчитывается отдельно на основе качества источника, уверенности сопоставления и подтверждённости рёбер пути. В ответе API показывать, какие факты подтверждены, а какие являются выводом/предположением.

## 8. Solution Engine и Scenario Simulator

### Решения

Для хакатона альтернативы — подготовленные демонстрационные записи, а не реальные коммерческие предложения. Поля: страна, срок, изменение себестоимости, оценка риска, совместимость, статус проверки.

Сортировка должна быть explainable: критерии и вклад каждого критерия доступны в ответе API. Пользователь видит компромисс, например «меньше риск — выше стоимость», а система не заявляет, что один вариант безусловно лучший.

### Симулятор

Минимальные входы:

- текущая доля выпуска, зависящая от поставки;
- запас в днях;
- ожидаемая задержка;
- выбранный альтернативный поставщик;
- оценка срока поставки и изменения себестоимости.

Минимальные выходы:

- риск остановки до и после сценария;
- изменение себестоимости;
- срок/задержка поставки;
- ключевые допущения;
- модель и время расчёта.

Расчёт должен быть повторяемым: одинаковый ввод даёт одинаковый ответ. Результат сохраняется на экране 17; пользователь отдельно подтверждает решение на экране 18.

Никакой расчёт не выдаётся за финансовую гарантию. Если исходных данных не хватает — API возвращает `insufficient_data` и список недостающих данных, а не придумывает число.

## 9. Telegram-бот: пользовательские требования

### Для владельца в личке

Бот присылает только события, подходящие под настройки подписки. Пример:

```text
🔴 ВЫСОКОЕ ВЛИЯНИЕ · СеверПром

Китай ограничивает экспорт электроники
Связано с Shenzhen X → компонент B → линия №2
Потенциально затронуто: 24% выпуска
Уверенность: средняя · 2 факта, 1 предположение

[Разобрать в приложении] [Пауза на 24 часа]
```

Кнопка «Разобрать в приложении» ведёт на карточку события, а не на общий dashboard. Если приложение не установлено, открыть web fallback или экран установки.

### Для рабочей группы

- группа подключается только явным действием владельца/администратора компании;
- по умолчанию отправляется короткая карточка без конфиденциальных финансовых деталей;
- полные расчёты доступны после авторизации в приложении;
- не читать переписку группы и не использовать её как источник данных;
- бот отвечает только на свои команды и callback-кнопки.

### Команды MVP

- `/start` — приветствие, безопасное начало подключения;
- `/help` — назначение бота и команды;
- `/settings` — показать текущие настройки/инструкцию перейти в приложение;
- `/mute` — временно остановить уведомления;
- `/unmute` — возобновить;
- `/status` — показать, подключён ли чат и к какой компании он привязан (в личке пользователя; в группе — только без утечки чувствительных данных).

Настройка подписок выполняется в мобильном приложении. Бот не должен быть единственным местом, где можно отключить уведомления.

### Частное и групповое подключение

Telegram требует, чтобы пользователь сам начал личный диалог с ботом, прежде чем бот сможет отправлять ему личные сообщения. Поэтому приложение должно открыть чат бота и попросить пользователя нажать Start; backend не обещает подключение только по Telegram username. Для групп пользователь добавляет бота и подтверждает привязку группы. Глубокие ссылки Telegram поддерживают передачу ограниченного параметра запуска; использовать только случайный одноразовый pairing token, не JWT и не сведения о компании. [Telegram Bot Features](https://core.telegram.org/bots/features)

В разработке локально можно использовать long polling; на публичном стенде — HTTPS webhook с проверкой секретного заголовка. `getUpdates` и активный webhook одновременно использовать нельзя. [Telegram Bot API](https://core.telegram.org/bots/api)

### Защита от спама и повторов

- не слать каждое событие: только при достижении пользовательского порога;
- дедупликация по паре «компания + событие + канал»;
- cooldown для повторных обновлений одного события;
- учитывать quiet hours, часовую зону и mute;
- ограничивать частоту сообщений на пользователя/группу;
- хранить статус каждой отправки и причину ошибки;
- на временной ошибке повторять отправку с задержкой; на заблокированный бот/чат деактивировать канал и показать это в приложении.

### Условия подключения к Telegram

Для MVP первым реализовать личный чат владельца. Групповое подключение — следующий приоритет в той же итерации, если остаётся время: оно требует отдельного подтверждения chat id и проверки доступа. Не отправлять чувствительные сведения компании в группу по умолчанию.

---

## 10. Очередь уведомлений и доставка

При появлении или пересчёте `event_impact` сервис уведомлений:

1. проверяет порог, тип события, расписание тишины и статус подписки;
2. формирует короткий payload и deep link на экран события;
3. записывает задачу в `notification_outbox` в той же транзакции;
4. worker отправляет сообщение через Telegram Bot API;
5. сохраняет `sent`, `retry` или `failed` и ответ Telegram.

Outbox нужен, чтобы событие и уведомление не расходились при перезапуске процесса. Не выполнять сетевую отправку Telegram внутри транзакции создания события.

---

## 11. Безопасность и приватность

- пароль только в виде сильного хэша, никогда не хранить открытым текстом;
- access/refresh-токены с коротким сроком и безопасной ротацией;
- авторизация каждого запроса с проверкой membership в `company_id`;
- пользователь не должен получать профили/события чужой компании по подмене ID;
- Telegram bot token — только в secret/env, не в репозитории, логах или клиенте;
- одноразовые Telegram pairing tokens хранить как hash, ограничивать срок и использовать один раз;
- не помещать личные данные или внутренние показатели компании в deep-link параметр;
- проверять входящий webhook по секретному заголовку, если используется webhook;
- логировать действия без паролей, токенов и полного содержимого чувствительных полей;
- владелец может отключить канал и удалить связь Telegram;
- group chat не получает финансовых подробностей до отдельного подтверждения в настройках.

## 12. Seed-данные для демо

Команда `seed_demo` должна быть идемпотентной: повторный запуск не создаёт дубли.

### Компания

- ООО «СеверПром», производство оборудования;
- продукт: промышленные насосы;
- поставщик: Shenzhen X, Китай;
- компонент: электронный модуль B;
- площадка: завод №1, Тула;
- критичная линия: линия №2, 24% выпуска;
- рынки: Россия и СНГ;
- закупочные валюты: RUB, CNY, USD;
- кредиты/параметры — только демонстрационные и необязательные.

### Три демонстрационных сценария продукта

1. **Экспортные ограничения:** риск поставки → альтернативы → симулятор.
2. **Изменение ключевой ставки:** связь с отмеченным финансовым фактором → сценарное сравнение расходов; результат обозначается как оценка.
3. **Новая рыночная возможность:** изменение условий импорта/рынка → связь с продуктом и рынком → рекомендуемый следующий шаг.

Для каждого события обязательно добавить source stub с названием демонстрационного источника, датой и URL/меткой-заглушкой. Не изображать фейковые ссылки на официальные источники как реальные.

## 13. Нефункциональные требования

- REST JSON API под мобильный клиент;
- документация OpenAPI доступна в dev;
- миграции БД воспроизводимы с чистой базы;
- ответ большинства demo-endpoint’ов укладывается в 500 мс на локальной среде;
- листинги поддерживают limit/cursor pagination;
- UTC для хранения дат, отображение локального времени задаёт клиент/настройка пользователя;
- backend не зависит от того, запущен ли Telegram: основная цепочка в приложении работает без бота;
- ошибки и логи пригодны для диагностики на демо;
- секреты не коммитятся.

## 14. Тестирование и критерии приёмки

### Обязательные тесты

1. Регистрация, подтверждение и вход.
2. Пользователь не может прочитать чужой профиль компании.
3. Создание профиля и сохранение прогресса между шагами онбординга.
4. Пропуск финансового шага не блокирует готовность профиля.
5. Seed-событие строит корректный путь `событие → Shenzhen X → компонент B → линия №2`.
6. Подтверждённые факты и предположения возвращаются отдельно.
7. Одинаковый запрос симуляции даёт одинаковый результат и модельную версию.
8. Решение и action items сохраняются и читаются после перезапуска.
9. Повторное событие не создаёт повторное Telegram-сообщение при одинаковом dedupe key.
10. Просроченный/использованный pairing token не подключает Telegram.
11. Бот отключён — API и мобильная цепочка продолжают работать.

### End-to-end критерий

Тестовый пользователь проходит регистрацию или входит под demo-пользователем, создаёт/открывает «СеверПром», видит событие об ограничении экспорта, открывает объяснимую цепочку, выбирает поставщика A из Таиланда, получает сравнение, сохраняет решение и получает одно личное Telegram-уведомление с переходом прямо к этому событию.

Все числа и источники демо явно помечены как демонстрационные. При недостатке данных система сообщает об этом, а не выдумывает точные потери.

## 17. Что сделать в первый рабочий день

1. Зафиксировать стек, общий репозиторий и соглашения API.
2. Поднять Postgres, миграции, `/health` и OpenAPI.
3. Наполнить seed-данными компанию, узлы, связи, одно событие и три альтернативы.
4. Согласовать с frontend три первых ответа API: profile, dashboard, event detail.
5. Только после прохождения пути «событие → решение» добавлять дополнительные события и интеграции.

### Главный технический принцип

**Сначала честная и объяснимая цепочка на одной компании, затем масштабирование.** AI может помогать формулировать краткие объяснения, но факты, оценки, источники и решения должны оставаться структурированными, проверяемыми и отделёнными друг от друга.
